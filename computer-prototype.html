Design Evolution

Make the starting point easier to find. Both participants needed help finding AITrace in the paper prototypes. The computer version adds a labelled entry above each changed block and an overview at the top of the file. Users can open a review directly from the code.

Keep the explanation close to the code. Both participants preferred the pop-up layout. We kept its link between code and explanation, but use a panel beside the editor in this version. It stays open while users inspect the code, and highlights the block being discussed. Users can follow their code selection or pin an explanation. This differs from the paper pop-up and still needs testing.

Make larger changes easier to review. P2 liked the plus/minus markers but wondered how longer replacements would appear. The plugin keeps short previews in the code and shows the full original and suggested block in the panel. Previous/Next controls and a review count help users work through the changes. Extra examples and assumptions are available when needed; free-form follow-up questions are not implemented.

Prototype Implementation

The prototype is a VS Code extension with a Python sample file on the left and an AITrace review panel on the right. Accepting, rejecting, undoing, navigation, and progress updates work without someone changing the interface behind the scenes. Accepting a change updates and saves the sample file.

AITrace is meant to help review output from another AI assistant. For this study, Simulate AI Output loads fixed suggestions and explanations. Pending suggestions are previewed beside the original code; they only enter the file when accepted. This version does not connect to a live AI, explain arbitrary files, run code, or answer new questions.

There are two bundled cases: a one-change pass/fail practice case and a three-change task-list case. Each demo opens a fresh sample copy. The original samples stay unchanged, and participants do not need to open their own projects.

User Population

Our target users are university students who use AI tools for programming assignments. We focus on students who want to check how the code works before accepting a change, as described in our Structural Reviewer persona.

Participants should be able to read basic Python and have some experience with desktop VS Code. They do not need to have used AITrace. Record their experience with coding, VS Code, and AI tools in the pre-test questionnaire so it can help explain any difficulties during the session.

Usability Goals

We want users to spot changes, understand the review controls, and move through a case without losing their place. The targets below are starting points for the test, not results we have already achieved.

GoalWhat we checkTarget
VisibilityCorrectly identified, missed, and incorrectly identified changed blocks.Find all three changed blocks in the task-list case without help.
LearningTask completion, time, wrong actions, and help needed on first use after practice.Open the review within 30 seconds and carry out each instructed accept/reject action within 30 seconds, without help.
ManageabilityEffort rated from 0 (no effort) to 5 (extreme effort), plus signs of confusion or losing one's place.Average effort of 2 or less. Participants can move through all three changes without losing track of which one is open.
Review efficiencyTime to find an assigned explanation, wrong destinations, and repeated searching.Find the assigned explanation within 30 seconds without help. Record reading time separately.
SatisfactionUsefulness and satisfaction ratings from 0 (lowest) to 5 (highest), with comments about each.Average of at least 4 for both usefulness and satisfaction.

The 30-second targets apply to short actions with visible controls after a practice case. They leave room to look around but should reveal repeated searching. They exclude time spent reading explanations or judging code. The rating targets mean that we are aiming for low effort and a clearly positive experience. Check these targets in a pilot before testing with the other team, and document any changes.

Usability Evaluation Plan

The testing team will run a timed usability test with students, then inspect the interface for usability problems. The instructions below let them do both without help from our team.

Activity 1: Formal Usability Test

People and Equipment

One examiner introduces the session and reads the tasks. An observer records actions, timing, comments, and any help given. Use a computer with desktop VS Code 1.85 or later and the linked extension installed, a timer, the manual above, and the three forms below. Record the operating system and VS Code version. A screen recording is useful if the participant agrees; written notes and a timer are enough if he does not.

Before the Session

  1. Check that the plugin starts and both samples load. Do not use a participant's personal project.
  2. Explain consent, including any recording, and collect the pre-test questionnaire.
  3. Let the participant read the manual and try Practice - Course result. Allow questions during practice and note any help. Do not include this in the timed results.
  4. Run AITrace: Start Demo, choose Review - Pending task list, and click Simulate AI Output. Leave all three decisions pending, close only the AITrace panel tab, and leave the sample source visible. Task 1 begins from this state.
  5. Start recording only if agreed. Read the introduction and task instructions below.

During the Session

Read each task as written. Start timing when you finish the instruction, and stop when the task is complete or the participant stops. For Task 3, stop the navigation timer when the right explanation opens, then time reading separately. For Task 4, time each accept/reject action separately. Record code discussion separately from these short action times.

Stay neutral and ask the participant to think aloud. Do not point out controls or finish actions for him. If he cannot complete a short action within two minutes, ask whether he wants to stop or receive help. Allow up to three minutes for Task 2. Record the unfinished attempt and any help given; keep assisted completion separate from independent success. A reminder to think aloud does not count as interface help.

If a technical problem interrupts the test, pause the timer and record it separately from user errors. For an unresponsive extension, reload the VS Code window and open a fresh task-list demo. Record the lost state and repeat the interrupted task after restoring its starting state. Do not combine time from the interrupted attempt with the new attempt.

Test Script

Introduction

“Thanks for joining us. Today we are trying AITrace, a tool for reviewing AI code changes. We are testing the tool, not you. Please tell us what you are looking for and anything that feels confusing. You can take a break, skip a question, or stop at any time.”

“The examples and AI responses are prepared in advance. You do not need to write or run code. In this case, the goal is to show only unfinished tasks, make the count match that list, and keep the original task order.”

Task 1: Open AITrace

“Open AITrace's review panel for this sample.”

Observer check: the panel opens for the task-list sample. Time from the end of the instruction until the panel is visible.

Task 2: Identify Code Changes

“Find the three suggested changes and tell us what each would change in the code.”

Observer check: the participant identifies the incomplete-task filter, the remaining-task count, and the alphabetical sort. Record any missed blocks or unchanged code identified as a change.

Task 3: Find and Read an Explanation

“Find the explanation for the change to the remaining-task count. Tell us when you have finished reading it, and briefly explain why the count changes.”

Observer check: the panel shows “Count the same tasks that Pending displays.” Stop navigation timing here and record reading time separately. The count uses the Pending list rather than the full task list; record the participant's explanation without treating a quick answer as proof of understanding.

Task 4: Accept and Reject Changes

Read these instructions one at a time, allowing the participant to finish each action:

  1. “Accept the change that excludes completed tasks.”
  2. “Accept the change that makes the remaining count match the Pending list.”
  3. “Reject the alphabetical sort so the tasks stay in their original order.”

Observer check: the filter and count are accepted, the sort is rejected, and the review count reaches 3 of 3. The source uses a filtered Pending list and len(pending), with visible = pending. Record the time and any wrong action for each instruction. This task checks use of the controls; it does not measure whether users independently judge a suggestion correctly.

Neutral Prompts

Use prompts such as “What are you looking for?”, “What did you expect to happen?”, or “Please keep telling us what you are thinking.” If help is needed, write down exactly what you said.

After the Tasks

Ask for an effort rating from 0 (no effort) to 5 (extreme effort) after each task. At the end, collect the post-test questionnaire and ask: “What felt easy?”, “What was confusing or distracting?”, and “What would you change?” Thank the participant and stop any recording.

What to Record

Use one sheet per participant. For each task, note whether he finished independently, finished with help, or did not finish. Add the elapsed time, wrong actions, help given, and any comments or pauses worth following up. A wrong selection or decision counts as an error; a broken control or extension crash is a technical failure.

Keep navigation time separate from reading and code discussion. Report missed changed blocks separately from wrong clicks. Use recordings only when consented to; otherwise, rely on the timer and notes. The plugin's optional AITrace: Export Session Log command can support the notes, but its events do not prove that someone read or understood an explanation. Export before switching cases or reloading, since a new session clears the in-memory log.

Reporting Instructions

Summarize participants' relevant experience, test setup, and any departures from the plan. For each task, report independent and assisted completions, unfinished attempts, individual times, and errors. Compare these with the targets above. Include effort and satisfaction ratings, useful comments, and technical failures. Tie each suggested improvement to something observed in the test, and avoid drawing broad conclusions from a small group.

Activity 2: Heuristic Evaluation

Two members of the testing team will inspect AITrace separately using Nielsen's ten usability heuristics. Each should try the four tasks above, then explore undo, pinning, examples, closing and reopening the panel, and resetting a sample. Afterward, compare notes, combine duplicate issues, and agree on which problems need attention first.

What to Look For

HeuristicCheck in AITrace
Visibility of system statusCan you tell which change is open, whether it is pending, accepted, or rejected, and how many changes remain?
Match between system and real worldDo the labels and plus/minus previews make sense when reading code?
User control and freedomCan you change a decision with Undo, accept/reject again, or close the panel without deciding?
Consistency and standardsDo labels, colors, and review states mean the same thing in the source and panel?
Error preventionAre Accept and Reject easy to tell apart? Does reset warn before clearing work?
Recognition rather than recallCan you see the relevant code and explanation without remembering an earlier screen?
Flexibility and efficiency of useCan you move between changes, follow code, pin an explanation, and jump back to the source easily?
Aesthetic and minimalist designDoes the panel show what you need without distracting controls or repeated information?
Help users recognize, diagnose, and recover from errorsAfter a wrong decision or manual edit, is it clear what happened and how to continue?
Help and documentationAre the labels and manual enough to get started without asking the examiner?

Severity and Reporting

Rate each issue from 0 to 4: 0 is not a usability problem; 1 is cosmetic; 2 causes a small delay or confusion; 3 makes a task difficult; 4 blocks an important task with no reasonable workaround. Consider how often the problem occurs and whether users can recover.

For each issue, record the heuristic, where it happened, the steps to reproduce it, the severity, and a possible fix. Keep each evaluator's original notes as well as the combined list. If you disagree about severity, record why.

How We Will Use the Results

The test should show whether users can find AITrace, connect explanations to code, and make decisions without help. We will use the timings, comments, and inspection findings to decide what to change next. These tests evaluate the prepared review workflow; they cannot establish how well AITrace would explain new code from a live AI assistant.
