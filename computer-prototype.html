Prototype Implementation

User Population

The target users are university students who use AI tools while completing programming assignments. The evaluation focuses on the Structural Reviewer persona: a student who wants to understand and evaluate AI-generated changes rather than accept them without review.

Participants should have basic experience reading code and using a web browser. They do not need prior experience with AITrace. The study examines whether participants can discover and use the interface, not whether they already know how the system works.

Usability Goals

The table below summarizes the usability goals for the AITrace computer prototype. Each goal is linked to a quantitative measurement and a possible goal that will guide the evaluation. Time targets apply to short interface actions and exclude time spent reading explanations or analyzing code.

Goal Description Measurement Possible Goal
Visibility Users can identify which parts of the code were added, removed, or modified by an AI suggestion. Number of correctly identified changes, missed changes, and incorrect identifications. Participants correctly identify all required changed regions in the prepared code case without operational assistance.
Learning First-time users can complete the main review tasks with little or no guidance. Task completion rate, task completion time, number of errors, and number of prompts required. Participants complete each benchmark task without operational assistance. Participants start AITrace within 30 seconds and complete an instructed accept or reject action within 30 seconds.
Manageability Users do not feel overwhelmed by the amount of code, explanations, or review controls. Post-task effort rating on a 0–5 scale, where 0 = no effort and 5 = extreme effort; observed hesitation, confusion, and skipped explanations. Participants give an average effort rating of 2 or lower and review the prepared changes without skipping explanations or losing track of the interface.
Review Efficiency Users can find, inspect, and decide on code changes without unnecessary repeated actions. Task completion time, navigation errors, and number of repeated or redundant interactions. Participants locate an assigned explanation within 30 seconds. Participants complete each short interface action without repeated searching or unnecessary navigation.
User Satisfaction Users find the explanations, review controls, and navigation features useful and are satisfied with the review experience. Post-test usefulness and satisfaction ratings on a 0–5 scale, along with qualitative feedback. Participants give an average rating of 4 or higher for both usefulness and satisfaction.

These possible goals are provisional and will be checked during a pilot session before the independent evaluation. They measure interface usability and do not evaluate the correctness of AI-generated code or programming learning.

Usability Evaluation Plan

The evaluation includes two complementary activities: a formal laboratory usability test and a heuristic evaluation. The usability test examines whether representative users can complete the core AITrace tasks. The heuristic evaluation identifies interface problems that may not appear during task-based testing.

Activity 1: Formal Usability Test

Examiners and Roles

  • Lead Examiner: Explains the session, reads tasks verbatim, manages timing, and answers only procedural questions.
  • Observer: Records task outcomes, time, errors, hesitations, backtracking, technical failures, and participant comments.

Equipment Required

  • Computer with [FILL IN: browser and version].
  • AITrace computer prototype from [FILL IN: repository or hosted link].
  • Stopwatch or timer application.
  • Task log sheet, printed or digital.
  • User manual and installation guide.
  • Pre-test and post-test questionnaires.
  • Phone or screen-recording device, if participants consent.

Prototype Handling Guidelines

  • Use only the provided manual; do not modify, debug, or redesign the prototype during testing.
  • Open the required prepared code case before the participant begins.
  • Record technical failures separately from participant errors.
  • If the prototype crashes or becomes unresponsive, reload or restart it using the documented recovery procedure and resume from the last completed task.
  • Do not change the interface, task wording, or evaluation procedure during a session.

Examiner Instructions

Before the Session
  1. Obtain informed consent, including consent for audio or video recording if used.
  2. Explain: “We are testing the usability of AITrace. We are evaluating the system, not your programming ability or personal performance.”
  3. Conduct the pre-test questionnaire.
  4. Open the prototype and prepared test case.
  5. Position the recording device to capture the screen and participant actions.
  6. Begin recording and start the session timer.
During the Session
  1. Read each task verbatim from the task script.
  2. Do not provide hints beyond the standard introduction and user manual.
  3. Encourage participants to think aloud while remaining neutral.
  4. Start the stopwatch when a task begins and stop it when the participant indicates completion or the examiner ends the task.
  5. Record success, time, errors, hesitations, backtracking, and technical failures for every task.
After the Session
  1. Stop recording.
  2. Ask the participant to complete the post-test questionnaire.
  3. Ask the open-ended feedback questions.
  4. Thank the participant and explain how their data will be used.

Examiner Conduct

Do Don’t
Stay neutral and encouraging. Explain how to perform a task.
Ask participants to verbalize their thoughts. Interrupt or complete actions for the participant.
Use a stopwatch or timer. Praise or criticize the participant’s performance.
Observe silently. Modify the interface during the test.
Record technical failures separately. Count a system failure as a participant error.

Test Script

Introduction Script

“Hello, and thank you for joining us. My name is [moderator name]. Today we are testing AITrace, a computer prototype designed to help users review code changes suggested by AI assistants.”

“Your participation is voluntary. You can skip a question, take a break, or stop at any time. Before we begin, please review the consent form. Do you have any questions about the study or the information we will collect?”

“Before we start, please complete the pre-test questionnaire. It will take about 5 minutes.”

Present the Code Case

“Here is the starting code and the required modification. An AI assistant has already produced a suggested change for this task. The response has been prepared for this study; it is not generated live.”

“Please use AITrace to review the suggested changes. You can think aloud while you work. Tell us what you are looking for, what you expect to happen, and anything that feels confusing.”

Task 1: Start AITrace Plugin

“Open AITrace so you can begin reviewing the suggested changes.”

Task 2: Identify Code Changes

“Look at the code shown in AITrace and identify the changes that have been suggested. Tell us which parts of the code were added, removed, or modified.”

Task 3: Locate and Read an Explanation

“Find the explanation for [FILL IN: X modification] and read it. Tell us when you have finished reading.”

Task 4: Accept or Reject a Suggestion

“Using AITrace, [accept / reject] the suggested change for [FILL IN: X modification].”

Neutral Prompts

  • “What are you looking for?”
  • “What are you expecting to happen?”
  • “What do you want to try next?”
  • “Please keep telling us what you are thinking.”

If the participant cannot continue, offer the minimum assistance needed and record its wording. Do not count neutral think-aloud reminders as interface guidance.

Final Reflection

  • What did you find easiest to do in AITrace?
  • What did you find confusing, difficult, or frustrating?
  • Which parts of the interface helped you understand the suggested changes?
  • Was anything missing, distracting, or unnecessary?
  • What improvement would you make?

Closing Script

“Thank you for your time and feedback. Your observations will help us decide what to improve in AITrace. That concludes the session.”

Measurements: What, How, and When

Measurements will be collected both during and after each task to evaluate performance and perception. Quantitative data, such as task completion time and number of errors, will provide an objective measure of usability. Qualitative data, including participant comments, facial expressions, and think-aloud observations, will offer insight into user perception, understanding, and satisfaction.

Measurement Description Collection Method
Task Completion Time Time taken to start AITrace, locate an explanation, or complete an instructed accept/reject action. Explanation-reading time is recorded separately. Stopwatch + screen recording
Error Count Number of incorrect actions, such as selecting the wrong control, identifying the wrong changed region, or accepting when rejection was instructed. Observer notes + predefined answer guide
Task Success Rate Whether the participant independently achieved the task goal without operational assistance. Assisted completions are recorded separately. Binary task log (Yes/No)
Qualitative Feedback Participant comments about what felt clear, confusing, useful, or difficult while reviewing AI-suggested code changes. Think-aloud recording + observer notes
Post-test Satisfaction Perceived usefulness, ease of use, and comfort when using AITrace to review AI-generated changes. Post-test questionnaire

Reporting

The evaluation report will include:

  • A participant summary, including demographics and session duration.
  • Quantitative results for completion, task time, errors, hesitations, backtracking, and technical failures.
  • Observations and qualitative notes for each task.
  • Post-test questionnaire results and open-ended feedback.
  • A distinction between usability problems, technical failures, and participant errors.
  • Design recommendations supported by the collected evidence.

Activity 2:Heuristic Evaluation

Both team members will independently inspect the AITrace interface using Nielsen’s 10 usability heuristics. Each evaluator will complete the four benchmark tasks, record usability violations, assign a severity rating, and propose an improvement. After individual reviews, the evaluators will meet to combine duplicate findings, resolve differences in interpretation, and prioritize issues by severity.

Procedure

  1. Each evaluator independently explores the AITrace interface.
  2. Each evaluator completes the same four benchmark tasks.
  3. Each evaluator records heuristic violations, affected interface elements, severity, and recommendations.
  4. Evaluators meet to consolidate duplicate findings and resolve differences in interpretation.
  5. The team prioritizes issues by severity and frequency across evaluators.

Heuristics and Applications

Heuristic Application in AITrace
Visibility of system status The interface should clearly show when AITrace is active, when changes are displayed, and when an accept or reject action has been completed.
Match between system and real world Labels and visual cues should use familiar programming and review terminology, such as “added,” “removed,” “modified,” “accept,” and “reject.”
User control and freedom Users should be able to review explanations before deciding and should be able to accept or reject suggestions without feeling locked into an action.
Consistency and standards Colors, icons, labels, and interaction patterns should be used consistently across added, removed, and modified changes.
Error prevention The interface should make accept and reject controls distinguishable and should prevent accidental irreversible actions where applicable.
Recognition rather than recall Users should recognize available actions and the meaning of visual cues rather than needing to remember them from earlier steps.
Flexibility and efficiency of use Users should be able to move between the code view, explanations, and review controls without unnecessary navigation.
Aesthetic and minimalist design The interface should present relevant information without overwhelming users with unnecessary visual detail.
Help users recognize, diagnose, and recover from errors If an action fails or cannot be completed, the interface should provide clear feedback and a way to recover.
Help and documentation Labels, tooltips, and the user manual should support first-time use without requiring the examiner to explain the interface.

Severity Meaning
